# Material 3 数据整理对笔记项目的帮助预估

记录日期：2026-11-10（UTC+8）  
文档性质：实施前的定性评估，不是性能实测报告，也不是已完成改造的说明。

## 评估前提

本次整理的“数据”指 Material 3 组件参数、版本适用范围、交互状态、动效规则、无障碍要求，以及它们与项目代码的对应关系；不指用户笔记内容或录音数据。现有导出材料包含笔记列表、编辑器、录音页面、设置及主题等模块，因此可以围绕真实页面安排改造，而不必重新建设整款应用。[file:25]

**整理本身不会改变已安装的软件。只有把核验后的规则落实为主题、公共组件、页面修改，并经过编译和回归测试，才会产生用户可见的变化。**下文的“较高”“中等”等为基于项目材料的预估，不代表量化实验结论。

## 收益预估

| 方面 | 整理并正确落地后的预期变化 | 预估收益与边界 |
|---|---|---|
| 视觉一致性 | 标题、正文、说明文字、按钮、圆角和页面层级更统一 | 较高；项目已有 MaterialTheme 和自定义控件，可在既有结构上归整，不必全部重写。[file:28][file:26][file:27] |
| 日常操作 | 主要操作、次要操作、选中和禁用状态更容易识别 | 中到较高；必须在真实笔记、录音、搜索流程中验证，不能只看静态设计稿。 |
| 点击与可读性 | 更系统地检查小图标、相邻按钮、字体放大及辅助功能 | 中到较高；触控面积与可见尺寸并不相同，需要结合布局与语义核验。[cite:118] |
| 动效体验 | 页面切换、展开收起和按压反馈采用明确规则 | 中等；统一节奏不等于帧率提高，仍需性能测量。[cite:648] |
| 后续开发 | 新页面能复用主题与组件，减少重新选择样式参数 | 较高的潜在收益；公共封装可固定项目需要的值并保留必要参数。[cite:280] |
| 版本维护 | 能区分官方默认、项目定制及特定版本行为 | 中到较高；仍需针对依赖升级复核，文档不能保证未来版本不发生变化。 |
| 新增业务能力 | 不会仅凭这些规范新增同步、识别或搜索算法 | 没有直接收益；这些能力需要另行设计与开发。 |

## 界面会怎样变化

**最值得期待的不是“换一套颜色”，而是同类信息和操作有同一种表达。**现有代码已使用 MaterialTheme，但也有 CapsulePair、PillButton、PillToggle、自定义导航和播放器控件；因此工作重点应是校准这些实现之间的规则，而不是把项目认定为完全没有设计体系。[file:28][file:27][file:26]

可优先建立“主标题、条目标题、正文、辅助信息、操作标签”的角色对应表，再把主题颜色、字体和形状映射到这些角色。Material 3 支持通过主题统一管理这些基础属性，但手写尺寸、固定颜色及自定义绘制部分仍需逐项接入，不会自动跟随所有主题调整。[cite:79][cite:647][cite:280]

对使用者而言，预期变化是：列表更容易浏览，编辑页的信息轻重更分明，设置与录音页不再需要重新适应另一套控件表达。这属于待验证的产品效果，不是对现有界面缺陷的全面诊断。

## 操作会怎样改善

项目中的 CapsulePair 是两个独立回调的自定义组合，主页导出代码又注明新建入口采用 FAB Menu；因此不能因为研究了 Split Button，就把所有双按钮或新建入口都强行换成 Split Button。应先核对当前真实入口、两项操作的关系与既有使用习惯，再决定采用、保留或调整。[file:28]

小控件的核验同样有实际价值。比如导出代码中 TodoCheck 的默认可见布局尺寸为 40dp，部分删除控件也采用紧凑尺寸，这些可列为优先检查点；但不能仅凭这一行代码就断言实际点击区域不达标，因为 Compose 可能在布局边界外扩展触控区域，邻近区域是否重叠也需要检查。[file:26][file:28][cite:118]

建议以“点得准、状态清楚、字体放大后不挤坏、读屏能识别用途和状态”为验收目标，不以“所有图标都画成同样大小”代替可用性判断。Android 的公开指导建议触控目标至少为 48dp，并区分绘制大小、布局留白和实际命中区域。[cite:117][cite:118]

## 开发会怎样改善

建议把整理成果变成“规则—代码—测试”对应关系，而不仅是一本文档。例如：某按钮使用什么语义、对应哪个公共组件、哪些页面复用、改动后需要复测哪些操作。Compose 的官方设计系统方案支持在 MaterialTheme 之上扩展主题，并通过自定义 composable 封装项目规则。[cite:280][cite:96]

这样后续增加页面时，开发者和 AI 可以依据同一个入口使用组件，而不是分别复制一套近似实现。预期有助于减少样式漂移和反复微调，但当前没有开发耗时基线，不能承诺节省某个百分比或固定天数。

版本记录也应服务于实际构建。现有依赖报告记录的 Material 3 最终解析版本为 1.5.0-beta02，Compose UI、Foundation 和 Animation 为 1.12.0；这可作为核验起点，但不能代替下一次交付前重新导出的依赖结果。[file:43]

## 不会自动解决什么

**不能把资料整理等同于软件性能、业务正确性或数据安全已经提升。**启动速度、列表掉帧、图片解码耗时和内存占用，需要分别建立基线并运行对应测量；动画规则更统一，也不代表已经消除卡顿。[cite:648]

现有图片查看器报告明确区分了“连续过渡可观察”与精确时长、性能结论，并记录部分真机场景未测；其中 220ms/160ms 为该轮项目取值，而非官方规范值。整理时应保留这种证据边界，不能把旧取值包装成官方默认，也不能把局部通过扩写成全软件通过。[file:46]

搜索修复报告记录过补丁编译问题和遮罩命中问题，最小修正后在模拟器通过，但该轮未完成真机验证。这说明规范只能减少一部分决策错误，实际修改仍必须经过代码检查、编译和运行验收。[file:49]

## 建议落地顺序

1. **先锁定当前基线。**核对最新源码、已应用补丁、依赖报告及构建方式，区分历史备选文件与实际编译文件；现有索引已说明 .m3version 文件仅供参考、不参与编译。[file:25]
2. **先做主题与公共控件。**将确认后的颜色角色、文字角色、形状及交互规则接入公共实现，避免每页分别修改。[cite:280][cite:647]
3. **优先打磨高频流程。**先处理首页列表、搜索和新建，再处理编辑器与插入内容；这是本次提出的实施优先级，不是已经确认的用户行为统计。
4. **再统一录音及辅助页面。**让播放、录音、设置和回收站沿用同一套公共规则，同时保留必要的场景差异。
5. **逐批回归后再交付。**保留已有键盘、图片查看与返回逻辑的测试依据，补齐新改动涉及的未测场景，不以外观更统一代替功能验收。[file:46][file:49]

## 如何判断值得

建议在相同设备、相同测试内容与相同配置下，保留改造前后的截图和操作记录，并建立以下验收项。这是后续测试方案，不是已有测试结果。

| 验收方向 | 观察办法 |
|---|---|
| 一致性 | 对照首页、编辑页、录音页和设置页，检查同角色文字、同类按钮和页面间距是否遵循已批准规则 |
| 任务完成 | 完整执行新建、搜索、插入图片、附加录音、删除恢复，记录步骤与失败情况 |
| 触控及无障碍 | 检查实际命中区域、相邻控件干扰、读屏用途与状态表达，并测试系统字体放大 |
| 回归风险 | 重测键盘已开时查看图片、搜索展开时返回、快速开关弹层等已有关键流程 |
| 性能 | 对同一启动与滚动流程测量，比较真实结果；不能用录屏帧率代替渲染性能指标。[cite:648] |
| 维护效果 | 在下一个新页面任务中记录复用范围、局部特例和返工原因，建立真实的开发成本基线 |

这一阶段最合理的成功标准，是把应用推进到“规则一致、操作可验证、修改可追溯”的状态，而不是承诺仅凭资料整理就达到某款商业产品的全部质量。实施初期会增加组件调整与回归测试工作，应按页面分批推进，不必等待所有 Material 3 组件都研究完才开始改善项目。
